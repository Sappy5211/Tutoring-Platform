## 1. Verdict summary

The operator's instinct is correct: the old chat UI is a reference, not a foundation. Here is the honest version of why, and what actually is worth lifting.

- **The command palette is the single best asset on disk.** It is genuinely production-grade — full ARIA combobox semantics, a hand-rolled dynamic-programming fuzzy matcher (not a greedy scan), focus trap, stale-index guards, zero extra dependencies. **LIFT**, near-verbatim.
- **The brain graph rendering engine is solid and directly reusable** for the topic/prerequisite knowledge graph. Canvas-based (not SVG), proper hover/selection neighborhood highlighting, reduced-motion handling, a documented and already-fixed race condition in the underlying library. **LIFT** the mechanism; **REBUILD** the domain vocabulary (node groups, colors) for topics/subtopics instead of carbon-compliance entities. Performance at "a few hundred nodes on a mid-tier Android phone" is **not verified anywhere in this codebase or its skill** — treat as an open risk, not a solved problem.
- **The chat/RAG "Ask" UI is the weakest of the four surfaces the operator wants reused, and for a specific structural reason, not just visual dating**: the backend it was built against is **not generative AI at all**. `backend/services/ask_service.py` docstring says outright: *"mock-mode retrieval + extractive... Synthesis is extractive (stitched passages)"* **[observed, `~/CarbonAnswer/backend/services/ask_service.py:1-6`]**, and the frontend's own response type pins `mode: 'extractive'` **[observed, `features/ask/types.ts:18`]**. There is no streaming anywhere in this feature — `askQuery()` is a single `await fetch` that resolves once **[observed, `features/ask/api.ts:30-43`]**; the app's only SSE client (`api/sse.ts`) is wired to a completely different feature (agent mission runs), not Ask. Message list, composer, conversation sidebar, and citation-chip UI are decent shells (state management via `useSyncExternalStore`/local hooks, no bugs found, `tsc --noEmit` and `oxlint` both clean) but they were never asked to render a token stream, so the piece the operator most needs for a DeepSeek-backed tutor — a streaming render pipeline — **does not exist in this codebase at all**. **REFERENCE-ONLY** for shell layout and citation UX; the actual streaming/generation plumbing must come from the `ai-chat-app-ui` skill instead, which was written for exactly this gap.
- **The `@xyflow/react` workflow canvas is two different things wearing one name**, and only one of them transfers. `pages/workflow/**` is a fixed, read-only pipeline visualization (`nodesDraggable={false}`, `nodesConnectable={false}` **[observed, `pages/workflow/components/WorkflowCanvas.tsx:186-187`]**) — this is the "watch a run happen" pattern, and it maps well onto a student-facing learning-path progress view. `pages/flows/**` is the actual editable drag-drop canvas (`useNodesState`/`useEdgesState`/`addEdge`, drag-and-drop from a palette **[observed, `pages/flows/components/FlowCanvas.tsx:1-16`]**) — this maps onto a teacher-authored curriculum/learning-path *builder*. Both are usable references; neither should be copied wholesale because both carry deep CarbonAnswer-specific vocabulary (agent families, DeepSeek/Anthropic tinting, CRP nodes).
- **The design token system is dark-mode-only, by explicit written decision** (`styles/tokens.css:1-3`: *"Dark-first 'command deck' system. Light mode is out of scope this phase."* **[observed]**; `html { color-scheme: dark; }` in both `tokens.css:73` and `index.css:54`). There is no light theme, no toggle, no `prefers-color-scheme` branch anywhere in `src/styles/` or `index.css`. For a homework/study app used by Indian students in daylight, on shared family devices, sometimes for printing notes — this is a real gap, not a nitpick. **ADAPT**: keep the token *architecture* (CSS custom properties → Tailwind `@theme` mapping is clean and worth keeping), but the color values need a light-mode pass from scratch; nothing here can simply be flipped.
- **The component kit (`components/ui/`) is a reasonable Radix-free primitive set** (Button, Card, Badge, Tabs, Drawer, Modal, Tooltip, Table, EmptyState, PageHeader, Sparkline, ConfidenceBadge, StatusDot, KeyValue, CodeBlock, ProgressRing — 16 components, one barrel file). Quality is consistently good: `forwardRef`, `aria-*` wired throughout, focus-visible rings, portal-based overlays with escape/focus handling. It is deliberately **not** shadcn/ui (no Radix primitives underneath) and is dark-only like everything else. Verdict: **ADAPT** — worth port-and-relight rather than starting over, but the operator should decide up front whether to keep this hand-rolled kit or switch to shadcn/ui (mission brief's own house-stack note doesn't mandate either); recommendation below.
- **Zustand usage (`store/app.ts`) is a clean, minimal reference pattern** — one store, `persist` middleware with explicit `partialize`, flat primitive/record state, no over-engineering. **LIFT** the pattern (not the content — none of the fields are relevant to an EdTech app).

## 3. Deep dive — the chat/RAG UI (`features/ask`, `pages/ask`)

**Files read in full:** `pages/ask/AskPage.tsx` (240 lines), `features/ask/{MessageBubble.tsx (169), Composer.tsx (120), ConversationSidebar.tsx (159), CorpusDrawer.tsx (208), SourceDrawer.tsx (91), CitationChip.tsx (49), SuggestionChips.tsx (27), ToastStack.tsx (41), api.ts (85), citations.ts (83), messageActions.ts (68), types.ts (61), useConversations.ts (127), useToast.ts (30)}`.

**Message rendering** — `MessageBubble.tsx:59-169`. User messages are a plain right-aligned bubble (`:73-79`). Assistant messages parse `[n]` citation markers out of the answer text via `parseCitationSegments` (`citations.ts:23-46`) and render each as an interactive `CitationChip` inline (`MessageBubble.tsx:114-127`). A confidence badge and a "Grounded on N documents" line follow (`:131-138`). A message-action row (copy / re-ask / view sources) renders from a declarative registry, not hardcoded buttons (`messageActions.ts:39-68`, consumed at `MessageBubble.tsx:89-94`) — this pattern (declarative actions filtered by `isAvailable`) is genuinely good and worth keeping regardless of what replaces the rest.

**Streaming** — does not exist. `askQuery()` (`features/ask/api.ts:30-43`) is `await fetch(...).then(res.json())`; the pending state is a single boolean flipped before/after (`AskPage.tsx:88-107`), rendered as a shimmering "Thinking through the corpus…" placeholder (`MessageBubble.tsx:37-57`) that is purely decorative — it is not consuming partial tokens, because there are none to consume. The one SSE client in the whole app (`src/api/sse.ts`) is used by `features/agentic/useMissionState.ts`, an unrelated feature, not by Ask.

**Citations** — `citations.ts:59-65` computes relevance as `score / topScore` (ratio to the best-scoring source in *that* answer, not an absolute threshold) — the code comment explains this is deliberate because raw BM25 scores aren't calibrated across queries. This reasoning is reusable even though BM25 itself won't exist in the new tutor.

**Input handling** — `Composer.tsx:23-42`: autosizing textarea (manual `scrollHeight` measurement, capped at 190px), Enter-to-send / Shift+Enter-for-newline, a file-attach button posting to an ingest endpoint. No slash-commands, no @-mentions, no LaTeX/formula input awareness — all of which the new tutor will need (formula input, or at minimum robust math-notation copy/paste).

**State management** — `useConversations.ts:16-125`: conversation list persisted to `localStorage` under a versioned key (`ask.conversations.v1`), plain `useState` + `useCallback`, defensive `try/catch` around `localStorage` access (private-mode safe). No message-tree/branching model (open-webui's edit-creates-a-sibling pattern, which the `ai-chat-app-ui` skill documents as gotcha #4) — a re-ask here just appends a new turn; editing a past question is not supported at all.

**Verdict:** REFERENCE-ONLY. The declarative message-actions pattern, the relative-scoring idea for citations, and the overall page layout (sidebar + thread + floating composer with a fade-scrim) are worth looking at while building the new tutor. Everything about actually talking to an LLM — streaming, message-tree branching, tool-call/reasoning display — must come from the `ai-chat-app-ui` skill's reference code, because this codebase never built it.

## 4. Deep dive — the brain graph (`features/graph`, `pages/brain`)

**Files read in full:** `features/graph/{GraphCanvas.tsx (315), ControlPanel.tsx (183), InspectorPanel.tsx (181), Legend.tsx (21), constants.ts (64), useGraphData.ts (36), types.ts (31)}`, `pages/brain/BrainGraphPage.tsx (135)`.

**Rendering approach** — `react-force-graph-2d`, wrapped in `GraphCanvas.tsx`. Nodes are drawn with a custom `nodeCanvasObject` callback (`:268-301`): a filled circle sized by `node.size * (forces.nodeSize / 6)`, a stroke ring for selected/hovered state, and a label drawn only past a zoom threshold (`LABEL_ZOOM_THRESHOLD = 2.2`, `constants.ts:64`) or always for the active node — this is the correct approach for label legibility at scale (don't render 300 text labels simultaneously). Links are colored by a `kind` enum and dimmed to 15% opacity when a hover/selection neighborhood is active elsewhere (`:249-256`).

**The one documented library bug, already fixed** — `react-force-graph`'s internal engine invokes `onZoom`/`onNodeHover` synchronously during its own render pass; committing a React state update straight from inside those callbacks throws "Cannot update a component while rendering a different component." The fix here (`:85-101`) stashes the latest value in a `useRef` and defers the actual `setState` to a `requestAnimationFrame`, with a value-changed guard so it doesn't spam re-renders. This exact bug + fix has already been extracted into the `obsidian-graph-view` skill's reference code (see §5) — meaning the *skill*, not the raw CarbonAnswer file, is the better source to build from, since it's already been generalized and had CarbonAnswer-specific naming stripped.

**Interaction** — pan/zoom (native to the library), hover-to-highlight-1-hop-neighborhood (`:143-160`), click-to-select (drives an `InspectorPanel`), double-click-to-center-and-zoom (`:210-225`), a resize-observer-driven responsive canvas (`:111-122`), and a `frozen`/reduced-motion mode that pins node positions once the simulation settles (`:181-208`) rather than animating forever. `InspectorPanel.tsx:44-50` caps its own searchable node list at 200 rendered rows (`.slice(0, 200)`) as a keyboard-accessible alternative to mouse hover — a real, working a11y affordance, not an afterthought.

**Performance at "a few hundred nodes on a mid-tier Android phone"** — **not verified**. This is a d3-force simulation running the physics on the JS main thread (not a web worker, not WASM), plus `<canvas>` 2D redraws every animation frame while the simulation is active. Nothing in this codebase or in the `obsidian-graph-view` skill's own gotcha list benchmarks this on a low-end device — the `reducedMotion` freeze mode (`:181-197`) mitigates *continuous* animation cost but does not change the one-time simulation cost of laying out N nodes, nor the per-frame canvas redraw cost while dragging/panning. **[assumed]** A few hundred nodes with a few hundred edges is very likely fine on canvas (this is well within what `react-force-graph-2d` is used for elsewhere), but "mid-tier Android phone" specifically has not been tested by anyone in this history. Recommend: build it, then load-test on an actual low-end/mid-tier Android device or emulator before committing to force-directed layout as the permanent solution — the fallback if it's too slow is a **static, pre-computed layout** (run the force simulation once at build/seed time server-side, ship fixed x/y coordinates, render with zero live simulation) which the `frozen` mode here already half-implements.

**Domain layer** — `constants.ts` node groups (`company`, `document`, `crp`, `passport`, `check`, `factor`, `obligation`, `agent`...) and colors are 100% CarbonAnswer-specific and must be replaced with an education vocabulary: e.g. `subject > unit > topic > subtopic`, with edge kinds like `prerequisite_of`, `part_of`, `related_to`. The mechanism (`GraphCanvas.tsx`) needs zero structural change to support this — it's already generic over `GraphNodeGroup`/`GraphLinkKind` typed as string unions.

**Verdict:** LIFT the canvas mechanism (preferably via the `obsidian-graph-view` skill's already-generalized reference code, not the raw CarbonAnswer files, since the skill has the identical fix with the CarbonAnswer naming already stripped out). REBUILD the domain layer. Flag performance-at-scale-on-low-end-Android as unverified and worth an early spike.

## 7. Honest gaps — what the operator does NOT already have

These surfaces have **zero prior art** in either the CarbonAnswer codebase or the house skills:

1. **Practice/quiz player and assessment/exam mode.** No question-rendering component, no answer-input UI (multiple choice, numeric, free-text, LaTeX-formula input), no timer/lockdown pattern, nothing. This is core to the platform and needs to be designed from a blank page.
2. **Mathematically-equivalent answer checking.** The mission's requirement that `0.5` == `1/2` == `2(x+3)` == `2x+6` is a symbolic-equivalence problem (needs a CAS — computer algebra system — on the backend, e.g. SymPy), not a UI problem, but the *UI* for showing "your answer was accepted as equivalent, here's why" has no precedent anywhere in-house either.
3. **Spaced-repetition flashcards.** No SRS scheduling algorithm, no card-flip/review-queue UI, nothing referencing Anki/RemNote-style review sessions anywhere in the skills list or CarbonAnswer.
4. **LaTeX/KaTeX formula rendering and input.** Not present anywhere — no math-notation rendering library is even in `package.json`. This needs to be added as a new dependency (KaTeX is the standard, lightweight choice) regardless of what else is lifted.
5. **Live teacher booking (scheduling, availability, Zoom, payment).** Zero prior art — no calendar component, no availability picker, no payment-flow UI, no video-call-join screen anywhere in CarbonAnswer or the skill list.
6. **Adaptive-mastery / spaced-review engine UI.** The mission brief explicitly wants "genuinely adaptive" difficulty targeting and review scheduling. Nothing in CarbonAnswer approximates this (its "adaptive" surfaces are agent-autonomy levels for a compliance pipeline, an unrelated domain). This needs new design, likely paired with a `dataviz` treatment for showing the student their own mastery curve.
7. **Light mode entirely.** Called out in §1 — every existing token, every existing component's Tailwind classes, is dark-only by written decision. Building for daylight/shared-device use means a real design pass, not a token flip.
8. **PDF export of notes.** The notes-editor requirement to export to PDF has no precedent — CarbonAnswer's only export feature is `features/runs/exportWorkflow.ts`, which downloads a JSON blob of pipeline state, not a rendered PDF.
9. **Indian payment rails, DPDP-Act-compliant consent UI, Indian curricula (CBSE/ICSE/JEE/NEET) taxonomy.** None of this exists in any form; entirely new domain modeling required, independent of any UI-layer decision in this lane.
